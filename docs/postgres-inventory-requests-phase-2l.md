# Phase 2L — PostgreSQL Inventory Requests

Incremental, additive migration of the MongoDB **InventoryRequest** entity to
PostgreSQL, following the architecture established in Phases 2A–2K.

## Scope

Only `InventoryRequest` is migrated in this phase:

- `backend/src/db/migrations/013_create_inventory_requests.sql`
- `backend/src/repositories/inventoryRequestRepository.js`
- `backend/src/services/inventoryRequestService.js`
- minimal controller integration (`inventoryRequestController.js`)
- tests + documentation

**Not migrated:** Purchase Orders, Goods Received Notes, Damage Notes, Assets,
Repairs, Rooms, HR (attendance/leaves/shifts/payroll), notifications, events,
poojas, prasadam or settings. Phase 2M has not started. MongoDB/Mongoose still
exists and remains the fallback path.

## Mongo model inspected

`backend/src/models/InventoryRequest.js` (Mongoose), plus every real usage of
`InventoryRequest` / `inventoryRequest` / `inventoryRequests` /
`inventory_requests` in the codebase:

- `backend/src/controllers/inventoryRequestController.js`
  - `createInventoryRequest` — standalone request submission
    (`InventoryRequest.findOne({ userId, itemName, status: 'Pending',
    createdAt: range })` duplicate guard, then `InventoryRequest.create({ ... })`).
  - `getInventoryRequests` — `InventoryRequest.find({ userId }).sort({ createdAt: -1 })`.
  - `getInventorySummary` — `InventoryRequest.find({ userId })`.
  - `updateInventoryRequestStatus` — approval (`save()` with `status:
    'Approved'`, `adminReason`, `reviewedBy`, `reviewedAt`, `approvedBy`,
    `approvedAt`) and rejection (`status: 'Rejected'`, `adminReason`,
    `rejectionReason`, `reviewedBy`, `reviewedAt`, `rejectedAt`).
  - `issueInventoryRequest` — cross-entity issuing: loads the request, finds
    the InventoryItem by exact `itemName` (case-insensitive regex), decrements
    `availableStock`, increments `issuedStock`, sets `status: 'Issued'`,
    `issuedAt`, and writes an `InventoryIssue` — all inside ONE Mongo
    multi-document transaction.
- `backend/src/controllers/devoteeController.js`
  `generateInventoryRequestsForBooking` — system-generated request creation
  during a booking, writing the request `_id` back into the booking's
  `templeMaterialRequests[].inventoryRequestId` on the same Mongo document.
- `backend/src/controllers/poojaBookingController.js` `createBooking` —
  system-generated request creation inside the pooja booking flow, writing the
  request `_id` back into `PoojaBooking` material requests.
- Frontend `frontend/src/pages/admin/InventoryManagement.jsx` renders request
  lists via `GET /admin/inventory-requests` and the priest/staff request
  screens filter by `userId`.

The `InventoryIssue` / `InventoryItem` models remain **Mongo-backed** (not
migrated in this phase).

### Intentionally omitted fields

None. Every persisted Mongo field in the `InventoryRequest` schema has an
explicit column.

### Nested-data decision

The MongoDB `InventoryRequest` schema contains no embedded arrays or objects —
only a flat set of scalar fields. Nothing needs to be normalized into child
tables and no JSONB column is required.

### Decided deliberately

- **No FKs at all.** The Mongo model declares `userId` as a plain **String**
  (real write paths store usernames / devotee emails / `'System'`), and
  `itemName` as a free-form String with no ObjectId ref. `user_id` is not the
  Phase 2A `users.id`, and `item_name` is not `inventory_items.id`; the users
  table is still Mongo-backed as the source of truth. A real FK would reject
  legitimate requests, so both columns are plain indexed TEXT — exactly like
  every user/item reference in Phases 2A–2K.
- **`quantity` NUMERIC + `>= 0` CHECK:** the Mongo schema declares `Number,
  required, min: 0` — zero is legal at the model layer (the HTTP controller
  additionally rejects `<= 0`, which is request validation, not a model
  restriction) and negatives are refused. Decimals round-trip exactly.
- **No unique constraint:** Mongo declares `userId: { index: true }` which is
  ordinary and **non-unique**, and no unique indexes on InventoryRequest. The
  duplicate-request guard is a controller-level `findOne` check, not a DB
  constraint.
- **`booking_material_requests.inventory_request_id` is NOT touched:** the
  Phase 2B-era decision to store the request id as plain TEXT in the booking
  material-requests table is preserved unchanged (additive migration).
- **Issue endpoint stays on Mongo (documented):** issuing is a cross-entity
  Mongo transaction (`InventoryItem` stock + `InventoryIssue` + request
  status) inside `mongoose.startSession`. InventoryIssue is not migrated, and
  PostgreSQL offers no such atomic cross-entity operation in this phase, so
  routing only the request side to PG would split a transaction across two
  databases. The standalone endpoints (create / list / summary /
  approve / reject) route through the service; the issuing flow and the
  system-generated booking flows stay on Mongoose with explanatory comments.

## Enums

| Field | Mongo enum | PG constraint | Default |
|---|---|---|---|
| `priority` | `['High', 'Medium', 'Low']` | `CHECK (priority IN ('High','Medium','Low'))` | `'Medium'` |
| `status` | `['Pending', 'Approved', 'Rejected', 'Issued']` | `CHECK (status IN ('Pending','Approved','Rejected','Issued'))` | `'Pending'` |

Exact values, exactly one default each. No extra values introduced.

## Quantity semantics

`quantity` is `Number, required, min: 0` in the Mongo schema; it maps to
`NUMERIC` with a `>= 0` CHECK. Zero is legal at the model layer, negatives are
rejected exactly like the Mongoose validator, and `NUMERIC` preserves the exact
scale (`10.50` stays `10.50`, `1000.125` stays `1000.125`). Tested round-trips:
`0`, `0.01`, `1`, `10.50`, `1000.125`, `123456.789`.

Monetary values: none — InventoryRequest is a pure quantity/status record, so
no money column exists.

## Fallback boundary (explicit)

```
InventoryRequest service
        │
        ├── PostgreSQL available (isDbConnected AND isPostgresConnected)
        │       ↓
        │   PostgreSQL repository (inventoryRequestRepository)
        │
        └── otherwise
                ↓
            MongoDB/Mongoose model (InventoryRequest)
```

- The datasource seam (`dbConfig.isDbConnected` in `src/config/db.js`) is read
  **at call time** by both the service and the repository — a test or future
  caller can swap the function after the modules are loaded and the very next
  call routes accordingly. It is not captured at require time.
- The PostgreSQL gate additionally requires `isPostgresConnected()` to return
  true, so an entirely unavailable PostgreSQL can never take the app down.
- No dual writes.
- No production Mongo → PostgreSQL migration.
- No Mongo document deletion.
- No global switch to PostgreSQL.
- No cross-database transaction claims — the issue flow transaction is
  documented as intentionally Mongo-only.

## Indexes and the queries they serve

| Index | Actual application query | Reason |
|---|---|---|
| `(user_id)` | Mongo schema `userId: { ..., index: true }` (ordinary, non-unique); `getInventoryRequests` / `getInventorySummary` filter by `userId` | mirrors the Mongo schema index and the dominant read path |
| `(created_at DESC)` | `getInventoryRequests` — `find({ userId }).sort({ createdAt: -1 })`; the admin `GET /admin/inventory-requests` list sorts by `createdAt` DESC | covering index for the default list scan |
| `(user_id, status, created_at DESC)` | `createInventoryRequest` duplicate guard — `findOne({ userId, itemName, status: 'Pending', createdAt: range })` | leading `user_id` equality + `status` equality + `createdAt` range behave like Mongo's per-key indexes for this exact predicate |

No speculative indexes were added. No `status`-only, `item_name`, `priority`,
or `expected_date` index: no application query filters solely on those without
a leading `userId`.

## Repository methods

`backend/src/repositories/inventoryRequestRepository.js`:

- `create` — validates userId/userName/itemName/unit/reason/purpose (required),
  quantity (required number, `>= 0`), priority/status enums, then a single
  parameterized `INSERT … ON CONFLICT (id) DO NOTHING`, re-read by `findById`.
- `findById` — parameterized `SELECT … WHERE id = $1`.
- `findOne` — filter builder + `ORDER BY created_at DESC, id DESC` limit 1.
- `findMany` — filters + whitelisted `ORDER BY` + `LIMIT`/`OFFSET`.
- `updateById` — dynamic parameterized `UPDATE` over allowed columns, returns
  the re-read row; `null` for missing ids.
- `count` — `SELECT COUNT(*)::int`.
- `destroy` — `DELETE … RETURNING id`, boolean existence report.

Filter support mirrors the real callers plus Mongo-compatible `$in`
semantics: `userId` (=`/$in`), `status` (=`/$in`, enum-validated), `itemName`
(=`/$in`), `priority` (=`/$in`, enum-validated), `id` (=`/$in`), `createdAt`
(`$gte/$gt/$lte/$lt`), `expectedDate`, `approvedAt`, `reviewedAt`,
`rejectedAt`, `issuedAt` ranges, and `quantity` ranges. An empty `$in` array
matches nothing, exactly like Mongo. Sorting is restricted to an explicit
whitelist (`createdAt`, `updatedAt`, `expectedDate`, `rejectedAt`,
`approvedAt`, `reviewedAt`, `issuedAt`, `quantity`, `priority`, `status`,
`userId`, `userName`, `role`, `itemName`, `unit`); unknown keys fall back to
`created_at DESC, id ASC` without throwing. All SQL is parameterized; no user
input is ever interpolated into SQL.

## Service

`backend/src/services/inventoryRequestService.js` exposes the same surface as
the other Phase 2 services: `isConnected`, `usePostgres`, `validate`, `create`,
`findById`, `findOne`, `findMany`, `updateById`, `count`, `destroy`. It
validates/normalizes the payload once (userId/userName/itemName/unit required,
quantity required and `>= 0`, reason/purpose schema-required, role defaults to
`'Staff'`, requestedBy/adminReason/rejectionReason/approvedBy/reviewedBy
default to `''`, priority defaults to `'Medium'`, status defaults to
`'Pending'`, expectedDate defaults to now), then routes to the PostgreSQL
repository when the datasource seam is connected AND PostgreSQL is reachable,
or to the existing Mongoose model otherwise.

## Integration

`inventoryRequestController.js`

- `createInventoryRequest` — duplicate check + create now route through
  `inventoryRequestService.findOne` / `inventoryRequestService.create`.
- `getInventoryRequests` — `findMany({ filter: query, sort: { createdAt: -1 } })`.
- `getInventorySummary` — `findMany({ filter: { userId: id } })`.
- `updateInventoryRequestStatus` — approval/rejection route through
  `findById` and `updateById`; the transition rules (cannot re-approve,
  cannot reject an approved request, cannot re-reject) are preserved exactly.
- `issueInventoryRequest` — **intentionally stays on Mongoose** (cross-entity
  Mongo transaction), documented inline; the model import is retained.
- `devoteeController.generateInventoryRequestsForBooking` and
  `poojaBookingController.createBooking` — system-generated request creations
  **intentionally stay on Mongoose** (they write the request id back into the
  same Mongo booking document), documented inline.
