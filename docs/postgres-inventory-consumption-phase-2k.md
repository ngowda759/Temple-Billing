# Phase 2K — PostgreSQL Inventory Consumption

Incremental, additive migration of the MongoDB **InventoryConsumption**
entity to PostgreSQL, following the architecture established in Phases 2A–2J.

## Scope

Only `InventoryConsumption` is migrated in this phase:

- `backend/src/db/migrations/012_create_inventory_consumption.sql`
- `backend/src/repositories/inventoryConsumptionRepository.js`
- `backend/src/services/inventoryConsumptionService.js`
- minimal controller integration (`inventoryIssueController.js`)
- tests + documentation

**Not migrated:** Inventory Logs, Inventory Requests, Purchase Orders, GRNs,
Damage Notes, Assets, Repairs, Rooms, HR (attendance/leaves/shifts/payroll),
notifications, events, poojas, prasadam or settings. Phase 2L has not started.
MongoDB/Mongoose still exists and remains the fallback path.

## Mongo model inspected

`backend/src/models/InventoryConsumption.js` (Mongoose). Real usages traced
in:

- `backend/src/controllers/inventoryIssueController.js`
  - `completeUsage` creates one consumption record when an inventory issue is
    completed: `InventoryConsumption.create({ issue, item, itemName, userId,
    userName, role, issuedQuantity, usedQuantity, returnedQuantity, unit,
    purpose, remarks })`.
  - `getConsumptionReports` lists the latest 100 consumptions sorted by
    `date` descending: `InventoryConsumption.find().sort({ date: -1
    }).limit(100)`.
- `backend/src/routes/adminInventoryRoutes.js` — `GET
  /admin/inventory/reports/consumption` (admin "Consumption Tracking" tab).
- `backend/src/routes/priestRoutes.js`, `backend/src/routes/staffRoutes.js` —
  `GET /inventory-issues`, `GET /inventory-issues/:userId`,
  `POST /inventory-issues/:id/complete` drive the write path above.
- Frontend `frontend/src/pages/admin/InventoryManagement.jsx` renders
  `_id`, `createdAt`, `userName`, `itemName`, `usedQuantity`, `unit`,
  `remarks` from the consumption report response.

The `InventoryIssue` model (`backend/src/models/InventoryIssue.js`) is the
write-time source for `issue`, `userId`, `userName`, `role`, `issuedQuantity`,
`unit` and `purpose`. It remains **Mongo-backed** (not migrated in this phase).

## Mongo → PostgreSQL field mapping

| Mongo field | Type/default | PostgreSQL column | PG type | Required/default | Constraint/index | Notes |
|---|---|---|---|---|---|---|
| `_id` | ObjectId | `id` | `TEXT` | PK | PRIMARY KEY | 24-hex Mongo-compatible id generated by the repository |
| `issue` | ObjectId ref `InventoryIssue`, optional | `issue_id` | `TEXT` | nullable | `idx_inventory_consumptions_item_date`-adjacent (query support below) | InventoryIssue is still Mongo-backed → **no FK** (no fake FKs to non-migrated tables) |
| `item` | ObjectId ref `InventoryItem`, **required** | `inventory_item_id` | `TEXT` | NOT NULL | `REFERENCES inventory_items(id) ON DELETE RESTRICT` + `idx_inventory_consumptions_item_date` | Real FK — `inventory_items` exists (Phase 2H). RESTRICT preserves Mongo's delete semantics: Mongo leaves consumptions orphaned when an item is deleted, so PG refuses the delete instead of cascading (least behaviour-changing, identical to Phases 2I/2J) |
| `itemName` | String, **required** | `item_name` | `TEXT` | NOT NULL | — | stored as the item's name at write time |
| `userId` | String, **required**, `index: true` | `user_id` | `TEXT` | NOT NULL | `idx_inventory_consumptions_user_id` | **String** in the Mongo schema (NOT the User ObjectId ref); `completeUsage` stores the issuing user's username → **no FK**. The index mirrors the non-unique `index: true` |
| `userName` | String, **required** | `user_name` | `TEXT` | NOT NULL | — | — |
| `role` | String, **required** (free-form, no enum) | `role` | `TEXT` | NOT NULL | — | — |
| `issuedQuantity` | Number, **required**, `min: 0` | `issued_quantity` | `NUMERIC` | NOT NULL | `CHECK (issued_quantity >= 0)` | zero legal, negatives rejected (Mongo min: 0); decimals round-trip exactly |
| `usedQuantity` | Number, **required**, `min: 0` | `used_quantity` | `NUMERIC` | NOT NULL | `CHECK (used_quantity >= 0)` | zero legal, negatives rejected |
| `returnedQuantity` | Number, **required**, `min: 0` | `returned_quantity` | `NUMERIC` | NOT NULL | `CHECK (returned_quantity >= 0)` | zero legal, negatives rejected |
| `unit` | String, **required** | `unit` | `TEXT` | NOT NULL | — | copied from the issue at write time; no CHECK in the Mongo schema |
| `purpose` | String, default `""` | `purpose` | `TEXT` | NOT NULL DEFAULT '' | — | default preserved |
| `remarks` | String, default `""` | `remarks` | `TEXT` | NOT NULL DEFAULT '' | — | default preserved |
| `date` | Date, default `Date.now` | `date` | `TIMESTAMPTZ` | NOT NULL DEFAULT now() | `idx_inventory_consumptions_date` | instant preserved |
| `createdAt` / `updatedAt` | timestamps | `created_at` / `updated_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT now() | — | — |

### Intentionally omitted fields

None. Every persisted Mongo field in the `InventoryConsumption` schema has an
explicit column.

### Decided deliberately

- **`item` FK with `ON DELETE RESTRICT`:** Mongo's `deleteInventoryItem`
  (`InventoryItem.findByIdAndDelete`) never touches consumptions — they remain
  orphaned. A cascade would destroy data Mongo keeps, so PostgreSQL instead
  refuses to delete an item that still has consumptions. This is the least
  behaviour-changing strategy and is identical to Phases 2I (`inventory_batches`)
  and 2J (`inventory_logs`).
- **`issue` as plain TEXT, no FK:** `InventoryIssue` is not a migrated entity
  in Phase 2K. A FK to a non-existent PG table would be a fake FK; plain
  indexed TEXT matches the convention for every Mongo-backed reference so far
  (`grn`/`supplier` on `inventory_batches`, polymorphic `reference_id`).
- **`userId` as plain TEXT, no FK:** the Mongo schema declares `userId` as a
  **String**, not an ObjectId ref, and `completeUsage` stores the issuing
  user's username. The `users` table (Phase 2A) is also still Mongo-backed, so
  a real FK would reject rows whose username is not a PG user id. Plain TEXT.
- **No JSONB:** the Mongo schema has no embedded objects/arrays.
- **No unique constraints:** the Mongo schema declares no unique indexes on
  InventoryConsumption, so none are created.

## Enums

None. The `InventoryConsumption` schema declares no enum fields (`role`,
`unit` and `purpose` are free-form strings), unlike `InventoryLog.action` or
`InventoryItem.status`. Nothing to preserve beyond exact free-form TEXT.

## Quantity semantics

`issuedQuantity`, `usedQuantity` and `returnedQuantity` are `Number,
required, min: 0` in the Mongo schema. They map to `NUMERIC` with a
`>= 0` CHECK — zero is legal (an issue can be completed with everything
returned), negatives are rejected exactly like the Mongoose validator, and
`NUMERIC` preserves the exact scale (`10.50` stays `10.50`, `1000.125` stays
`1000.125`). Tested round-trips (each quantity column): `0`, `0.01`, `1`,
`10.50`, `1000.125`, `123456.789`.

Monetary values: none — InventoryConsumption is a pure quantity record, so no
money column exists.

## Fallback boundary (explicit)

```
InventoryConsumption service
        │
        ├── PostgreSQL available (isDbConnected AND isPostgresConnected)
        │       ↓
        │   PostgreSQL repository (inventoryConsumptionRepository)
        │
        └── otherwise
                ↓
            MongoDB/Mongoose model (InventoryConsumption)
```

- The datasource seam (`dbConfig.isDbConnected` in `src/config/db.js`) is read
  **at call time** by both the service and the repository — a test or future
  caller can swap the function after the modules are loaded and the very next
  call routes accordingly. It is not captured at require time.
- No dual writes.
- No production Mongo → PostgreSQL migration.
- No Mongo document deletion.
- No global switch of Inventory to PostgreSQL.
- No cross-database transaction claims.

## Indexes and the queries they serve

| Index | Actual application query | Reason |
|---|---|---|
| `(date DESC)` | `InventoryConsumption.find().sort({ date: -1 }).limit(100)` (`inventoryIssueController.getConsumptionReports` — admin "Consumption Tracking" tab) | covering index for the latest-100 report scan |
| `(user_id)` | Mongo schema `userId: { ..., index: true }` (ordinary, non-unique); the staff/priest inventory-issue screens list by `userId` | mirrors the Mongo schema index |
| `(inventory_item_id, date DESC)` | per-item consumption inspection: `find({ item: id }).sort({ date: -1 })` pattern | covering index for the per-item scan with date ordering |

No speculative indexes were added. No `issue_id` index: no PG query filters on
the Mongo-backed InventoryIssue.

## Repository methods

`backend/src/repositories/inventoryConsumptionRepository.js`:

- `create` — validates item/itemName/userId/userName/role/unit (required),
  issuedQuantity/usedQuantity/returnedQuantity (required number, `>= 0`),
  then a single parameterized `INSERT … ON CONFLICT (id) DO NOTHING`, re-read
  by `findById`.
- `findById` — parameterized `SELECT … WHERE id = $1`.
- `findOne` — filter builder + `ORDER BY date DESC, created_at DESC` limit 1.
- `findMany` — filters + whitelisted `ORDER BY` + `LIMIT`/`OFFSET`.
- `updateById` — dynamic parameterized `UPDATE` over allowed columns, returns
  the re-read row; `null` for missing ids.
- `count` — `SELECT COUNT(*)::int`.
- `destroy` — `DELETE … RETURNING id`, boolean existence report.

Filter support mirrors the real callers plus Mongo-compatible `$in`
semantics: `item` (=`/$in`), `issue` (=`/$in`), `userId` (=`/$in`), `id`
(=`/$in`), `date` (`$gte/$gt/$lte/$lt`), `createdAt` ranges, and
issued/used/returned quantity ranges. An empty `$in` array matches nothing,
exactly like Mongo. Sorting is restricted to an explicit whitelist (`date`,
`createdAt`, `updatedAt`, `issuedQuantity`, `usedQuantity`,
`returnedQuantity`, `item`, `itemName`, `userId`, `userName`, `role`);
unknown keys fall back to `date DESC, created_at DESC` without throwing. All
SQL is parameterized; no user input is ever interpolated into SQL.

## Service

`backend/src/services/inventoryConsumptionService.js` exposes the same
surface as the other Phase 2 services: `isConnected`, `usePostgres`,
`validate`, `create`, `findById`, `findOne`, `findMany`, `updateById`,
`count`, `destroy`. It normalizes/validates the payload once (item/itemName/
userId/userName/role/unit required, the three quantities required and `>= 0`,
`purpose`/`remarks` default to `""`, `date` defaults to now), then routes to
the PostgreSQL repository when the datasource seam is connected AND
PostgreSQL is reachable, or to the existing Mongoose model otherwise.

## Integration

The two `InventoryConsumption` callers in
`inventoryIssueController.js` were routed through the service with the
smallest possible diff, mirroring how Phase 2G wired `devoteeController`:

- `completeUsage` → `inventoryConsumptionService.create({ ... })` (same
  payload as before).
- `getConsumptionReports` →
  `inventoryConsumptionService.findMany({ filter: {}, sort: { date: -1,
  createdAt: -1 }, limit: 100 })` (semantically identical to the original
  `find().sort({ date: -1 }).limit(100)`).

The `InventoryIssue`/`InventoryItem` paths in the controller are untouched —
they remain on Mongoose exactly as before. No other entity was switched.
