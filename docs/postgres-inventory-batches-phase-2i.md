# Phase 2I — PostgreSQL Inventory Batches

Incremental, additive migration of the MongoDB **InventoryBatch** entity to
PostgreSQL, following the architecture established in Phases 2A–2H.

## Scope

Only `InventoryBatch` is migrated in this phase:

- `backend/src/db/migrations/010_create_inventory_batches.sql`
- `backend/src/repositories/inventoryBatchRepository.js`
- `backend/src/services/inventoryBatchService.js`
- tests + documentation

**Not migrated:** Inventory Logs, Inventory Consumption, Inventory Requests,
Purchase Orders, GRNs, Damage Notes, Assets, Repairs, Rooms, HR, notifications,
events, poojas or settings. Phase 2J has not started.

## Mongo model inspected

`backend/src/models/InventoryBatch.js` (Mongoose). Real usages traced in:

- `backend/src/controllers/inventoryWorkflowController.js`
  - `approveGRN` creates one batch per GRN line.
  - `logKitchenProduction` consumes raw-material batches FIFO.
- `backend/src/models/DamageNote.js` — `batch` ref (no query loads batches
  through it).

## Mongo → PostgreSQL field mapping

| Mongo field | Type/default | PostgreSQL column | PG type | Required/default | Constraint/index | Notes |
|---|---|---|---|---|---|---|
| `_id` | ObjectId | `id` | `TEXT` | PK | PRIMARY KEY | 24-hex Mongo-compatible id generated by the repository |
| `item` | ObjectId ref `InventoryItem`, **required** | `inventory_item_id` | `TEXT` | NOT NULL | `REFERENCES inventory_items(id) ON DELETE RESTRICT` + `idx_inventory_batches_item_status_expiry` | Real FK — `inventory_items` exists (Phase 2H). RESTRICT preserves Mongo's delete semantics: Mongo leaves batches orphaned when an item is deleted, so PG refuses the delete instead of cascading (least behaviour-changing) |
| `batchNumber` | String, required, trim | `batch_number` | `TEXT` | NOT NULL | part of UNIQUE `(inventory_item_id, batch_number)` | trims; `approveGRN` falls back to `AUTO-${Date.now()}` |
| `grn` | ObjectId ref `GoodsReceivedNote` | `grn` | `TEXT` | nullable | — | GRN still Mongo-backed → no FK (no fake FKs) |
| `purchasePrice` | Number, default 0, no min | `purchase_price` | `NUMERIC` | NOT NULL DEFAULT 0 | — | negatives allowed exactly like Mongo; exact scale preserved |
| `manufacturingDate` | Date | `manufacturing_date` | `TIMESTAMPTZ` | nullable | — | instant preserved |
| `expiryDate` | Date | `expiry_date` | `TIMESTAMPTZ` | nullable | in FIFO index | instant preserved; FIFO order key |
| `originalQuantity` | Number, required, min 0 | `original_quantity` | `NUMERIC` | NOT NULL | `CHECK (original_quantity >= 0)` | decimals allowed (fractional kitchen quantities) |
| `currentQuantity` | Number, required, min 0 | `current_quantity` | `NUMERIC` | NOT NULL | `CHECK (current_quantity >= 0)` | decimals allowed |
| `status` | enum, default `'Active'` | `status` | `TEXT` | NOT NULL DEFAULT `'Active'` | `CHECK (status IN (...))` | 6 values preserved exactly |
| `supplier` | ObjectId ref `InventorySupplier` | `supplier` | `TEXT` | nullable | — | InventorySupplier Mongo-backed → no FK |
| `createdAt` / `updatedAt` | timestamps | `created_at` / `updated_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT now() | `idx_inventory_batches_created_at (DESC)` | — |

### Decided deliberately

- **`item` FK with `ON DELETE RESTRICT`:** Mongo's `deleteInventoryItem`
  (`InventoryItem.findByIdAndDelete`) never touches batches — they remain
  orphaned. A cascade would destroy data Mongo keeps, so PostgreSQL instead
  refuses to delete an item that still has batches. This is the least
  behaviour-changing strategy consistent with the Mongo schema: batch records
  are never silently deleted by the FK.
- **`grn` / `supplier` as plain TEXT, no FK:** their targets are still
  Mongo-backed in this phase. No fake FK is created.
- **No JSONB:** the Mongo schema has no embedded objects/arrays.
- **No silent field drops:** every persisted Mongo field is mapped above.
- **Batch number uniqueness:** preserved as the Mongo compound unique
  `{ item: 1, batchNumber: 1 }` — multiple batches per item allowed, same batch
  number across different items allowed.
- **Pre-save hook mirror:** the Mongo `pre('save')` transitions
  (`currentQuantity === 0` → `Consumed`, past `expiryDate` → `Expired`, both
  only when `status === 'Active'`) are replicated in the repository **create**
  path only, exactly like Mongoose (which never runs `pre('save')` for
  `findByIdAndUpdate`).

## Fallback boundary (explicit)

```
InventoryBatch service
        │
        ├── PostgreSQL available (isDbConnected AND isPostgresConnected)
        │       ↓
        │   PostgreSQL repository (inventoryBatchRepository)
        │
        └── otherwise
                ↓
            MongoDB/Mongoose model (InventoryBatch)
```

- The datasource seam (`dbConfig.isDbConnected` in `src/config/db.js`) is read
  **at call time** by both the service and the repository — a test or future
  caller can swap the function after the modules are loaded and the very next
  call routes accordingly. It is not captured at require time.
- No dual writes.
- No production Mongo → PostgreSQL migration.
- No Mongo document deletion.
- No global switch of Inventory to PostgreSQL.
- No cross-database transaction claims.

## Indexes and the queries they serve

| Index | Actual application query | Reason |
|---|---|---|
| `(inventory_item_id, status, expiry_date, created_at)` | `InventoryBatch.find({ item, status: 'Active' }).sort({ expiryDate: 1, createdAt: 1 })` (FIFO consumption in `logKitchenProduction`) | covering index for the FIFO scan |
| `(created_at DESC)` | default batch listings / createdAt ordering | keeps recent-batch lookups incremental |
| UNIQUE `(inventory_item_id, batch_number)` | Mongo `{ item: 1, batchNumber: 1 }` unique | duplicate batch number per item rejected |
