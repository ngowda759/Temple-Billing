# Phase 2M — PostgreSQL Purchase Orders

Incremental, additive migration of the MongoDB **PurchaseOrder** entity to
PostgreSQL, following the architecture established in Phases 2A–2L.

## Scope

Only `PurchaseOrder` (and its embedded `items[]`) is migrated in this phase:

- `backend/src/db/migrations/014_create_purchase_orders.sql`
- `backend/src/repositories/purchaseOrderRepository.js`
- `backend/src/repositories/purchaseOrderItemRepository.js`
- `backend/src/services/purchaseOrderService.js`
- minimal controller integration (`inventoryWorkflowController.js` createGRN)
- tests + documentation

**Not migrated:** Goods Received Notes, Damage Notes, Assets, Repairs, Rooms,
HR (attendance/leaves/shifts/payroll), notifications, events, poojas, prasadam
or settings. Phase 2N has not started. MongoDB/Mongoose still exists and
remains the fallback path.

## Mongo model inspected

`backend/src/models/PurchaseOrder.js` (Mongoose), plus every real usage of
`PurchaseOrder` / `purchaseOrder` / `purchaseOrders` / `purchase_orders` in the
codebase:

- `backend/src/controllers/inventoryWorkflowController.js` — `createGRN` is
  the **only** real consumer today: when a GRN is created with a
  `purchaseOrderId`, it loads the PO and flips `po.status = 'Partially
  Received'` (a simplified, approximated transition that does not recompute
  quantities). No route is currently wired to PurchaseOrder
  create/list/update endpoints, so the Mongoose model itself is effectively
  the write path and the status transitions are exercised only by this GRN
  flow.
- `backend/src/models/GoodsReceivedNote.js` — `purchaseOrder` is an ObjectId
  ref to PurchaseOrder stored on the GRN model. GRNs remain **Mongo-backed**
  (not migrated here); `inventory_grns` has no PostgreSQL table yet.
- `backend/src/models/AccountTransaction.js` — the polymorphic
  `reference_model` enum already includes `'PurchaseOrder'`, but no
  transaction is currently written with `referenceModel === 'PurchaseOrder'`
  (GRN approvals use `'GoodsReceivedNote'`). No FKs, indexes or columns are
  inferred from this enum listing.
- Frontend `frontend/src/pages/admin/` renders PO-adjacent lists through the
  existing inventory workflow endpoints; no separate PO create/list screen is
  wired to a backend route yet.

The `InventorySupplier` model stays **Mongo-backed** (no `suppliers` table
exists yet), so `supplier` is plain TEXT. The `InventoryItem` model **is**
PostgreSQL-backed (Phase 2H), so the item reference is a real FK.

## Mongo → PostgreSQL field mapping

| Mongo field | Type/default | PostgreSQL column | PG type | Required/default | Constraint/index | Notes |
|---|---|---|---|---|---|---|
| `_id` | ObjectId | `id` | `TEXT` | PK | PRIMARY KEY | 24-hex Mongo-compatible id generated by the repository |
| `poNumber` | String, **required**, `unique`, `trim` | `po_number` | `TEXT` | NOT NULL | `UNIQUE` (`purchase_orders_po_number_key`) | the sole unique index on the model — mirroring Mongo exactly |
| `supplier` | ObjectId ref `InventorySupplier`, **required** | `supplier` | `TEXT` | NOT NULL | — | suppliers stay Mongo-backed (no `suppliers` table yet) → plain TEXT, **no FK** (same convention as `inventory_batches.grn_supplier`, `inventory_items.preferred_supplier`) |
| `items[]` | embedded array | `purchase_order_items` | child table | — | see child mapping | normalized; see "Nested-data decision" |
| `totalAmount` | Number, **required**, `min: 0` | `total_amount` | `NUMERIC` | NOT NULL | `CHECK (total_amount >= 0)` | STORED field (never derived by PG); exact scale round-trips |
| `status` | enum of 8 values, default `'Draft'` | `status` | `TEXT` | NOT NULL DEFAULT 'Draft' | `CHECK (status IN (...))` | enum preserved exactly, see "Enums" |
| `expectedDeliveryDate` | Date, optional | `expected_delivery_date` | `TIMESTAMPTZ` | nullable | `idx_purchase_orders_expected_delivery_date` | instant preserved; unset stays `NULL` (Mongo leaves it unset too) |
| `notes` | String, optional | `notes` | `TEXT` | nullable | — | — |
| `createdBy` | ObjectId ref `Employee`, optional | `created_by` | `TEXT` | nullable | — | optional unused reference; plain TEXT no FK (see "Decided deliberately") |
| `approvedBy` | ObjectId ref `Employee`, optional | `approved_by` | `TEXT` | nullable | — | optional unused reference; plain TEXT no FK |
| `createdAt` / `updatedAt` | timestamps | `created_at` / `updated_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT now() | `idx_purchase_orders_created_at` (created_at DESC) | — |

### Embedded item mapping (`purchase_order_items`)

The serialized embedded item keeps the Mongo sub-document shape (`_id` included —
embedded sub-documents in Mongo get their own `_id`).

| Mongo field | Type/default | PostgreSQL column | PG type | Required/default | Constraint/index | Notes |
|---|---|---|---|---|---|---|
| `items[]._id` | ObjectId (sub-doc) | `id` | `TEXT` | PK | PRIMARY KEY | 24-hex Mongo-compatible id |
| `items[].item` | ObjectId ref `InventoryItem`, **required** | `inventory_item_id` | `TEXT` | NOT NULL | FK → `inventory_items(id)` ON DELETE RESTRICT; `idx_purchase_order_items_inventory_item_id` | real FK: the target exists in PG (Phase 2H). RESTRICT — Mongo keeps order items orphaned when an item is deleted, so PG refuses instead of silently destroying parent data |
| `items[].orderedQuantity` | Number, **required**, `min: 1` | `ordered_quantity` | `NUMERIC` | NOT NULL | `CHECK (ordered_quantity >= 1)` | decimals allowed (existing inventory flows use fractional quantities) — NUMERIC preserves scale |
| `items[].unitPrice` | Number, **required**, `min: 0` | `unit_price` | `NUMERIC` | NOT NULL | `CHECK (unit_price >= 0)` | NUMERIC preserves exact money scale |
| `items[].totalPrice` | Number, **required**, `min: 0` | `total_price` | `NUMERIC` | NOT NULL | `CHECK (total_price >= 0)` | STORED (see "Stored vs derived") |
| `items[].receivedQuantity` | Number, default `0`, `min: 0` | `received_quantity` | `NUMERIC` | NOT NULL DEFAULT 0 | `CHECK (received_quantity >= 0)` | default preserved |
| array order | implicit | `position` | `INTEGER` | NOT NULL DEFAULT 0 | `idx_purchase_order_items_purchase_order_id_position` | preserves the embedded array order (same convention as `bill_items`) |
| — | sub-doc timestamps | `created_at` / `updated_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT now() | — | — |
| `items[].purchase_order_id` | parent link | `purchase_order_id` | `TEXT` | NOT NULL | FK → `purchase_orders(id)` ON DELETE CASCADE | embedded item rows belong to the order document → CASCADE deletes exactly what Mongo would remove with the PO (Phase 2C `bill_items` lifecycle) |

### Intentionally omitted fields

None. Every persisted Mongo field from the `PurchaseOrder` schema has an
explicit column above, and every persisted embedded item field has an explicit
column on `purchase_order_items`. The schema has no virtual-only fields.

## Nested-data decision

The MongoDB `PurchaseOrder` schema embeds `items[]` as sub-documents that are
relationally meaningful (each item references an `InventoryItem` and carries a
stock-facing quantity). Following the established convention from Phases 2C–2L,
the embedded array is normalized into a child table:

```
purchase_orders
    |
    +-- purchase_order_items  (ordered by position ASC)
```

Creation and item replacement are **atomic**: the repository wraps the parent
insert/update plus every child insert in one `BEGIN … COMMIT` transaction and
issues `ROLLBACK` on any failure, so no orphaned `purchase_order_items` rows
and no partial `purchase_orders` row can survive a failed write.

## Stored vs derived

Both `totalAmount` and `items[].totalPrice` are **stored** fields in the Mongo
model (`Number, required`) — the codebase never calculates line totals from
`quantity × unitPrice` anywhere. PostgreSQL therefore persists the exact values
the application writes and introduces **no** new accounting rule: no triggers,
no generated columns, no server-side computed totals.

## Enums

| Field | Mongo enum | PG constraint | Default |
|---|---|---|---|
| `status` | `['Draft','Pending Approval','Approved','Sent','Partially Received','Received','Cancelled','Closed']` | `CHECK (status IN ('Draft','Pending Approval','Approved','Sent','Partially Received','Received','Cancelled','Closed'))` | `'Draft'` |

Exact values, exactly one default. No extra values introduced (e.g. no
`'Ordered'`).

## Quantity and monetary semantics

All money (`unit_price`, `total_price`, `total_amount`) and quantities
(`ordered_quantity`, `received_quantity`) are `NUMERIC` — no `FLOAT`/`REAL`/
`DOUBLE PRECISION` anywhere. Tested round-trips:

- money: `0.01`, `10.50`, `1000.99`, `1000000.99`, `123456789.1234`
- quantities: `0`, `1.01`, `2`, `10.5`, `1000.125`

The CHECK constraints mirror the Mongo `min` validators exactly
(`orderedQuantity >= 1`, everything else `>= 0`).

## Fallback boundary (explicit)

```
PurchaseOrder service
        │
        ├── PostgreSQL available (isDbConnected AND isPostgresConnected)
        │       ↓
        │   PostgreSQL repository (purchaseOrderRepository
        │                         + purchaseOrderItemRepository)
        │
        └── otherwise
                ↓
            MongoDB/Mongoose model (PurchaseOrder)
```

- The datasource seam (`dbConfig.isDbConnected` in `src/config/db.js`) is read
  **at call time** by both the service and the repository — a test or future
  caller can swap the function after the modules are loaded and the very next
  call routes accordingly. It is not captured at require time.
- The PostgreSQL gate additionally requires `isPostgresConnected()` to return
  true, so an entirely unavailable PostgreSQL can never take the app down.
- No dual writes (proven by tests that spy on the Mongoose model while the PG
  path persists, and by tests that count PG rows while the Mongo fallback
  writes).
- No production Mongo → PostgreSQL migration.
- No Mongo document deletion.
- No global switch to PostgreSQL.

## Foreign keys (documented per column)

| Source column | Target table | Nullable | ON DELETE | Reason |
|---|---|---|---|---|
| `purchase_order_items.purchase_order_id` | `purchase_orders(id)` | NOT NULL | CASCADE | the embedded items array is part of the PurchaseOrder document in Mongo — deleting a PO must remove exactly what Mongo removes with it (same lifecycle as `bills`/`bill_items`, Phase 2C) |
| `purchase_order_items.inventory_item_id` | `inventory_items(id)` | NOT NULL | RESTRICT | Mongo keeps order items orphaned when an item is deleted; PG refuses the delete instead — identical reasoning to Phases 2I/2J/2K child tables |

**No fake FKs:** `supplier` → `InventorySupplier` (still Mongo-backed, no
`suppliers` table), `created_by`/`approved_by` → `employees` (optional unused
references the application never writes or filters; the employees PG table is
not a cutover datasource). All three are plain TEXT, matching the convention
used for every Mongo-backed reference in Phases 2A–2L.

## Indexes and the queries they serve

| Index | Actual application query | Reason |
|---|---|---|
| `purchase_orders(po_number)` UNIQUE | Mongo schema `poNumber: { unique: true }`; `findOne({ poNumber })` number lookups | the sole uniqueness semantic on the model, preserved exactly |
| `purchase_orders(status)` | status equals filters / list grouping; the createGRN `'Partially Received'` transition | primary PO list axis |
| `purchase_orders(expected_delivery_date)` | delivery-date ordering and range scans characteristic of PO review dashboards | surfaces incoming deliveries |
| `purchase_orders(created_at DESC)` | default `createdAt DESC` list ordering convention shared by every entity screen | covering index for the default list scan |
| `purchase_order_items(purchase_order_id, position)` | child rows always loaded per order in the embedded array order | covers the dominant read of the child table |
| `purchase_order_items(inventory_item_id)` | per-item purchase history | mirrors the per-item query axis used by every other inventory child table |

No invented uniqueness (the single `poNumber` unique is Mongo-real), and no
speculative indexes.

## Repository methods

`backend/src/repositories/purchaseOrderRepository.js`:

- `create` — validates poNumber/supplier (required), totalAmount (number,
  `>= 0`), status enum, normalizes the embedded items, then inserts the parent
  row AND every item row inside **one transaction** (`BEGIN`/`COMMIT`,
  `ROLLBACK` on any failure). Returns the re-read Mongo-shaped doc with the
  embedded `items` array.
- `findById` — parameterized `SELECT … WHERE id = $1`, hydrates items.
- `findOne` — filter builder + `ORDER BY created_at DESC, id DESC` limit 1.
- `findMany` — filters + whitelisted `ORDER BY` + `LIMIT`/`OFFSET`, hydrates
  each order's items.
- `updateById` — dynamic parameterized `UPDATE` over allowed columns, `null`
  for missing ids; embedded items are intentionally **not** silently replaced
  (that is `replaceItems`).
- `replaceItems` — atomic delete-all + insert of the child rows in one
  transaction (embedded-array replacement semantics).
- `count` — `SELECT COUNT(*)::int`.
- `destroy` — `DELETE … RETURNING id`, boolean existence report; the child
  rows cascade via `ON DELETE CASCADE`.

`backend/src/repositories/purchaseOrderItemRepository.js` (child table accessor
used by the parent repository):

- `findById`, `findByPurchaseOrderId` (ordered by `position ASC, created_at
  ASC, id ASC`), `findMany`, `create`, `updateById`, `count`, `destroy`, plus
  `normalizeItems`/`assertItem` validators shared with `create`.

Filter support (parent): `status` (`=`/`$in`, enum-validated), `supplier`
(`=`/`$in`), `poNumber` (`=`/`$in`), `id` (`=`/`$in`), `createdAt`,
`updatedAt`, `expectedDeliveryDate` (`$gte/$gt/$lte/$lt`), `totalAmount`
ranges. An empty `$in` array matches nothing, exactly like Mongo. Sorting is
restricted to an explicit whitelist (`poNumber`, `status`,
`expectedDeliveryDate`, `supplier`, `totalAmount`, `createdAt`, `updatedAt`);
unknown keys fall back to `created_at DESC, id ASC` without throwing. All SQL
is parameterized; no user input is ever interpolated into SQL.

## Service

`backend/src/services/purchaseOrderService.js` exposes the same surface as the
other Phase 2 services: `isConnected`, `usePostgres`, `STATUSES`, `validate`,
`create`, `findById`, `findOne`, `findMany`, `updateById`, `replaceItems`,
`count`, `destroy`. It validates/normalizes the payload once (poNumber/supplier
required, totalAmount required and `>= 0`, items with item/orderedQuantity/
unitPrice/totalPrice required and min matched to the schema, receivedQuantity
defaulting to 0, status defaulting to `'Draft'`, invalid enum rejected
pre-persistence), then routes to the PostgreSQL repository when the datasource
seam is connected AND PostgreSQL is reachable, or to the existing Mongoose
model otherwise.

## Integration

`inventoryWorkflowController.js` — `createGRN`:

- The `purchaseOrderService.findById(purchaseOrderId)` read and
  `purchaseOrderService.updateById(po._id, { status: 'Partially Received' })`
  transition replace the direct `PurchaseOrder.findById` + `po.save()` calls.
  The behaviour is unchanged (simplified status flip, no quantity
  recomputation, still non-transactional across the Mongo GRN write and the PO
  status update). GRN creation itself stays **Mongo-backed** (GoodsReceivedNote,
  InventoryBatch, AccountTransaction are not migrated in this phase).

No other controller, route, service or helper is modified.

  repository create/read/update/destroy/child-item routing to the real
