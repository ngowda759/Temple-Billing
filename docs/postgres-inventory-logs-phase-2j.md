# Phase 2J — PostgreSQL Inventory Logs

Incremental, additive migration of the MongoDB **InventoryLog** entity to
PostgreSQL, following the architecture established in Phases 2A–2I.

## Scope

Only `InventoryLog` is migrated in this phase:

- `backend/src/db/migrations/011_create_inventory_logs.sql`
- `backend/src/repositories/inventoryLogRepository.js`
- `backend/src/services/inventoryLogService.js`
- tests + documentation

**Not migrated:** Inventory Consumption, Inventory Requests, Purchase Orders,
GRNs, Damage Notes, Assets, Repairs, Rooms, HR (attendance/leaves/shifts/
payroll), notifications, events, poojas, prasadam or settings. Phase 2K has
not started.

## Mongo model inspected

`backend/src/models/InventoryLog.js` (Mongoose). Real usages traced in:

- `backend/src/utils/inventoryHelper.js`
  - `deductStock` / `addStock` create a log on every stock movement; used by
    `inventoryWorkflowController.approveGRN`, `logKitchenProduction`,
    `approveDamageNote`.
- `backend/src/controllers/inventoryItemController.js`
  - `createInventoryItem` logs the initial stock (`action: "Restocked"`).
  - `restockItem` logs each restock (`action: "Restocked"`).
  - `adjustStock` logs Damaged/Expired/Lost/Returned adjustments (`action`
    `Damage` / `Expire` / `Lost` / `Return`).
  - `getInventoryLogs` lists the latest 100 logs sorted by `date` descending.
- `backend/src/controllers/inventoryReportController.js`
  - `getDashboardMetrics` counts today's consumed logs.
  - `getInventoryReports` lists logs by date range.
  - `getItemDetails` lists an item's stock movement sorted by `date`
    descending.
- `backend/src/routes/adminInventoryRoutes.js` — `GET /inventory-logs`, the
  metrics/detailed-reports/item-details report routes.

## Mongo → PostgreSQL field mapping

| Mongo field | Type/default | PostgreSQL column | PG type | Required/default | Constraint/index | Notes |
|---|---|---|---|---|---|---|
| `_id` | ObjectId | `id` | `TEXT` | PK | PRIMARY KEY | 24-hex Mongo-compatible id generated by the repository |
| `item` | ObjectId ref `InventoryItem`, **required** | `inventory_item_id` | `TEXT` | NOT NULL | `REFERENCES inventory_items(id) ON DELETE RESTRICT` + `idx_inventory_logs_item_date` | Real FK — `inventory_items` exists (Phase 2H). RESTRICT preserves Mongo's delete semantics: Mongo leaves logs orphaned when an item is deleted, so PG refuses the delete instead of cascading (least behaviour-changing) |
| `action` | enum, **required** | `action` | `TEXT` | NOT NULL | `CHECK (action IN (...))` over the 10-value enum | allowed values preserved exactly |
| `quantity` | Number, **required**, **no min** | `quantity` | `NUMERIC` | NOT NULL | — | zero and negatives allowed exactly like Mongo; decimals round-trip exactly |
| `oldStock` | Number, default 0, no min | `old_stock` | `NUMERIC` | NOT NULL DEFAULT 0 | — | default preserved; negatives allowed |
| `newStock` | Number, default 0, no min | `new_stock` | `NUMERIC` | NOT NULL DEFAULT 0 | — | default preserved; negatives allowed |
| `user` | ObjectId ref `User`, optional | `user_id` | `TEXT` | nullable | — | users still Mongo-backed as source of truth → **no FK** (see below) |
| `date` | Date, default `Date.now` | `date` | `TIMESTAMPTZ` | NOT NULL DEFAULT now() | `idx_inventory_logs_action_date`, `idx_inventory_logs_date` | instant preserved |
| `createdAt` / `updatedAt` | timestamps | `created_at` / `updated_at` | `TIMESTAMPTZ` | NOT NULL DEFAULT now() | — | — |

### Intentionally omitted fields

- **`description`** — passed by every real write path (`inventoryHelper`,
  `inventoryItemController`) but **not declared in the Mongo schema**. Mongoose
  strict mode strips it, so it is never persisted in MongoDB. Mapping it to
  PostgreSQL would make PostgreSQL persist data Mongo drops, so it is
  deliberately not added. The repository accepts a caller-supplied
  `description` and drops it, exactly like the Mongo model.

No other fields are omitted.

### Decided deliberately

- **`item` FK with `ON DELETE RESTRICT`:** Mongo's `deleteInventoryItem`
  (`InventoryItem.findByIdAndDelete`) never touches logs — they remain
  orphaned. A cascade would destroy data Mongo keeps, so PostgreSQL instead
  refuses to delete an item that still has logs. This is the least
  behaviour-changing strategy and is identical to the Phase 2I decision for
  `inventory_batches`.
- **`user` as plain TEXT, no FK:** `users` exists in PostgreSQL (Phase 2A) but
  MongoDB remains its source of truth and user rows are routinely absent from
  the PG `users` table (registration/login still go through Mongoose). A real
  FK would reject legitimate logs whose Mongo user id is not present in PG —
  a hard break of the intended application semantics. This matches the
  convention applied to every user/employee reference in Phases 2A–2I
  (e.g. `account_transactions.recorded_by`, `pooja_bookings.created_by`).
- **No JSONB:** the Mongo schema has no embedded objects/arrays.
- **No unique constraints:** the Mongo schema declares no unique indexes on
  InventoryLog, so none are created. Logs are an append-only movement history.

## Enums

`action` — preserved exactly from the Mongo schema (no extra/missing values):

```
Added, Updated, Consumed, Restocked, Issue, Damage, Expire, Return, Lost, Adjusted
```

## Quantity semantics

`quantity`, `oldStock` and `newStock` are loose `Number`s with **no `min`** in
the Mongo schema, and the real flows use fractional kitchen quantities. They
map to `NUMERIC` with **no `>= 0` CHECK** — zero and negatives are legal
exactly as in Mongo — and `NUMERIC` preserves the exact scale (`10.50` stays
`10.50`, `1000.125` stays `1000.125`). Tested round-trips: `0`, `0.01`, `1`,
`10.50`, `1000.125`, `123456.789`.

Monetary values: none — InventoryLog is a pure stock-movement ledger, so no
money column exists.

## Fallback boundary (explicit)

```
InventoryLog service
        │
        ├── PostgreSQL available (isDbConnected AND isPostgresConnected)
        │       ↓
        │   PostgreSQL repository (inventoryLogRepository)
        │
        └── otherwise
                ↓
            MongoDB/Mongoose model (InventoryLog)
```

- The datasource seam (`dbConfig.isDbConnected` in `src/config/db.js`) is read
  **at call time** by both the service and the repository — a test or future
  caller can swap the function after the modules are loaded and the very next
  call routes accordingly. It is not captured at require time.
- No dual writes.
- No production Mongo → PostgreSQL migration.
- No Mongo document deletion.
- No global switch of Inventory to PostgreSQL.
- No cross-database transaction claims.

## Integration posture

All live InventoryLog callers (`inventoryHelper`, `inventoryItemController`,
`inventoryReportController`) remain on their existing Mongoose implementation.
This mirrors Phases 2H/2I exactly (the InventoryItem / InventoryBatch services
are also not wired into the controllers). Wiring the log service into those
flows while items and users are still Mongo-backed in the controllers would
either hit the `inventory_items` FK for ids absent from PG, or split a single
app flow across two databases — inconsistent and breakable. The repository/
service pair is the documented, tested seam: explicit callers (or a future
phase that also switches the item/user write paths) route InventoryLog
operations through it.

## Indexes and the queries they serve

| Index | Actual application query | Reason |
|---|---|---|
| `(inventory_item_id, date DESC)` | `InventoryLog.find({ item: id }).sort({ date: -1 })` (`inventoryReportController.getItemDetails` stock movement) | covering index for the per-item movement scan |
| `(action, date)` | `InventoryLog.find({ date: { $gte: today }, action: "Consumed" })` (`getDashboardMetrics` consumption count) | equality on action + range on date |
| `(date DESC)` | `InventoryLog.find().sort({ date: -1 }).limit(100)` (`getInventoryLogs`) and `find({ date: { $gte: startDate } })` (`getInventoryReports`) | recent-logs list and report date ranges |

No speculative indexes were added (no `user_id` index: no PG query filters on
it — `populate("user")` resolves through Mongo).

## Repository methods

`backend/src/repositories/inventoryLogRepository.js`:

- `create` — validates item (required), action (required + enum), quantity
  (required number), oldStock/newStock (number, default 0), then a single
  parameterized `INSERT … ON CONFLICT (id) DO NOTHING`, re-read by `findById`.
- `findById` — parameterized `SELECT … WHERE id = $1`.
- `findOne` — filter builder + `ORDER BY date DESC, created_at DESC` limit 1.
- `findMany` — filters + whitelisted `ORDER BY` + `LIMIT`/`OFFSET`.
- `updateById` — dynamic parameterized `UPDATE` over allowed columns, returns
  the re-read row; `null` for missing ids.
- `count` — `SELECT COUNT(*)::int`.
- `destroy` — `DELETE … RETURNING id`, boolean existence report.

Filter support mirrors the real callers: `item` (=`/$in`), `user` (=`/$in`),
`action` (=`/$in`, enum-validated), `id` (=`/$in`), `date`
(`$gte/$gt/$lte/$lt` ranges — used by the dashboard and reports), `createdAt`
ranges, `quantity` ranges. Sorting is restricted to an explicit whitelist
(`date`, `createdAt`, `updatedAt`, `quantity`, `action`, `item`, `user`);
unknown keys fall back to `date DESC, created_at DESC` without throwing.
All SQL is parameterized; no user input is ever interpolated into SQL.

## Service

`backend/src/services/inventoryLogService.js` exposes the same surface as the
other Phase 2 services: `isConnected`, `usePostgres`, `validate`, `create`,
`findById`, `findOne`, `findMany`, `updateById`, `count`, `destroy`. It
normalizes/validates the payload once, then routes to the PostgreSQL
repository when the datasource seam is connected AND PostgreSQL is reachable,
or to the existing Mongoose model otherwise.
